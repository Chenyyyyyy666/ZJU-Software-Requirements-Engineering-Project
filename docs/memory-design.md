# 数据与记忆设计草案

本文是职责 B 的 Proposal 配套设计，说明如何将 LoCoMo 对话转换为可追溯的结构化记忆，并向推理、Web 和评测模块提供检索结果。第一版采用按对话隔离的 JSON 存储和可替换的检索通道，优先跑通一段对话。

状态：已完成 `0.1` 数据契约、读取清洗、JSON 读写、逐轮基线、DeepSeek 抽取入口、BM25、MiniLM 向量检索与 RRF 混合检索。摘要视图及增量构建仍是设计提案。字段定义以 [interfaces.md](interfaces.md) 为准；[memory-example.json](memory-example.json) 是课件例子的人工整理结果。真实 DeepSeek 抽取质量及开发集上的检索召回率尚未验证。

## 课程要求与当前边界

依据用户提供的《0 - Project (2026).pdf》第 9–12 页：

- 课程使用 6 段对话，4 段开发、2 段独立测试，另 4 段可作扩展。当前仓库没有数据文件，具体编号待课程通知；不得将示例 `conv-26` 自动认定为开发集。
- 每条 Memory 保存内容、时间、来源，支持统一 JSON 导出；网页能够回看结构化记忆与原始证据。
- 针对问题检索历史记忆，再进行状态关系判断与有效记忆选择。历史事实应保持可追溯。
- 评测覆盖问答 F1、证据检索 Recall@K 和状态更新判断准确率；课件没有规定本文的具体字段、存储路径或检索融合公式。

本组另外约定使用纯文本、过滤图片链接、隔离评测标签，并按模块分工开发。B 主责数据结构、抽取与检索；C 主责查询分析、状态判断和回答；D 主责网页；E 主责评测。本文不改变这些分工。

## 数据准备与抽取

1. **检查输入**：从根目录 `locomo.json` 选择指定对话，核对其实际 ID、会话键、时间和轮次结构。适配器只输出对话文本及必要元数据，不把整个含 QA 的对象传给模型。
2. **保留证据**：记录 `conversation_id`、`session_id`、`turn_id`、`speaker`、`session_time` 和 `text`。保留原轮次 ID，不因过滤空文本或图片而重新编号。
3. **隔离标注**：QA、答案、gold evidence 和标注事件摘要不参与记忆构建；图片、图片链接及图片描述等多模态派生字段不参与抽取。实际字段白名单在取得课程数据后核对。
4. **分块抽取**：以会话为初始边界，超长会话再按轮次切块，必要时保留少量重叠上下文。每条 Memory 尽量只表达一个可独立验证的事实；可以引用多个来源轮次。块大小作为配置记录。
5. **规范化与校验**：保留人物名称、实体/属性/值、时间表达和来源；当前仅对字段与来源完全一致的抽取结果去重。不同来源的相似事实暂不合并，不同时间的状态分别保留，不能仅因实体与属性相同就覆盖旧值。
6. **持久化**：通过校验后保存 MemoryBundle，建立索引。格式错误或来源不存在的抽取结果进入错误记录并重试，不能静默写入或标记构建成功。

初始抽取按团队约定使用 DeepSeek 官方文本接口并关闭 thinking，具体可用模型标识在实现前确认。输入只包含对话证据；其中出现的指令也按待抽取文本处理。模型应返回约定结构，未明确出现的事实不补写，生成的答案也不回灌记忆。

## 时间与状态

`session_time` 表示说出这句话的时间，`event_time` 表示事件发生时间，两者不可互换。保留 `time_expression`，只有日期明确或可依据会话日期无歧义推导时才填写事件日期；无法解析时为 `null`。日期精度见接口草案，输入未提供时区时不擅自补为 UTC。

课件中会话时间为 `2023-10-22 09:55`，`last Friday` 在该锚点下可推导为 `2023-10-20`。示例将此推导写入事件时间；这是人工规范化演示，并非已运行的抽取结果。

例如课件中的“研究领养机构 → 提交申请 → 通过面试”，应分别保留为历史事实。B 不在构建时写入全局 `active` 或 `superseded`；C 根据问题和时间条件输出关系与有效 Memory ID。询问过去状态时，旧事实仍可能是所需答案依据。

## 存储与复现

运行产物使用现有已忽略目录，不新增顶层源码模块：

```text
locomo.json                              # 课程原始数据，本地存放
outputs/memory/<conversation_id>.json    # MemoryBundle 与来源证据
indexes/<hash>.json                      # 向量及模型/记忆版本元数据；BM25 在内存构建
cache/                                  # 抽取响应缓存
```

MemoryBundle 包含 `schema_version`、`conversation_id`、`build_info`、`source_turns` 和 `memories`。嵌入向量仅存索引，不放入课程交付 JSON。原始数据与批量输出不进入 Git；里程碑需要交付的 Memory JSON 由组长从本地输出中打包。

`build_info` 记录构建方式、输入哈希、抽取配置标识、模型和 prompt 版本。生产构建输入哈希按清洗后的原始轮次序列计算；缓存键同时包含配置、模型和 prompt 版本。相同输入与配置优先复用缓存，避免重复付费；改动数据或抽取配置后重建并记录版本。

一个 bundle 内 ID 唯一；持久化后不重排 ID。同一构建的缓存加载保持 ID 不变，重新抽取可能改变事实拆分，因此外部记录使用 `(conversation_id, build_id, memory_id)` 定位，不能跨构建直接混用 ID。索引必须记录相同 `build_id`，不匹配时重新构建。

## 检索与证据回溯

已实现 BM25 和向量检索。embedding 使用本地 `sentence-transformers/all-MiniLM-L6-v2`，默认 CPU，输出 384 维归一化向量；固定模型 revision 为 `1110a243fdf4706b3f48f1d95db1a4f5529b4d41`。只编码 Memory.content 和问题，计算余弦相似度，原始来源仍单独保留。模型与问题长度超过 256 token 时明确报错，避免截断证据。效果需在开发集验证。[官方模型说明](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2)

混合检索采用等权 Reciprocal Rank Fusion：每路先取 `candidate_k` 条，按 Memory ID 合并去重，以 `sum(1 / (60 + rank))` 合并排名，rank 从 1 开始，最后截取 `top_k`。BM25 分数和向量相似度不直接相加；分数仅用于当前查询排序，不解释为概率。两路原始分数和排名同时返回，便于评测与错误分析。

所有通道先限定 `conversation_id`。C 可以显式提供实体/属性过滤条件；查询分析失败或名称不确定时先不加硬过滤。初次检索结果交给 C 后，C 可请求同实体同属性的关联历史；扩展结果单列，保留初始 Top-K，便于 E 分别分析检索召回与扩展效果。B 不据“当前”一词自行删除旧状态。

每条命中保留通道排名、分数和 Memory 来源；Web 按来源读取原轮次。E 通过来源轮次集合对齐 gold evidence。指标定义由 E 与课程口径对齐：命中任一证据的 Hit@K 与覆盖全部 gold evidence 的 Recall@K 不应混称，本文只提供可计算两者的原始结果。

## OpenViking 的借鉴范围

可以参考 OpenViking 的工程组织方式。官方将资源、记忆和技能统一组织在虚拟文件系统中；本项目第一版只需要对话记忆及证据，不必同时引入技能管理。[官方介绍](https://docs.openviking.ai/en/getting-started/01-introduction)

下表左侧为官方设计，右侧为本项目提案，并不表示已集成 OpenViking：

| 官方设计 | 本项目的借鉴方式 |
| --- | --- |
| 按目录范围约束检索。[检索机制](https://docs.openviking.ai/en/concepts/07-retrieval) | 先按对话隔离，再按实体/属性组织可选查询视图；实际存储仍为 JSON |
| L0 摘要、L1 概览、L2 详细内容；L0/L1 是目录级辅助内容。[分层说明](https://docs.openviking.ai/en/concepts/03-context-layers) | 先检索简洁事实，按需读取对应原始轮次；实体时间线摘要作为后续可选视图。此映射是简化设计，不声称复刻三层实现 |
| 会话提交后归档，并执行摘要与记忆抽取，保留变更记录。[会话管理](https://docs.openviking.ai/en/concepts/08-session) | 保留证据和构建版本，后续可增加增量构建日志；第一版优先完成可复现的离线构建 |

当前官方检索文档描述的是受范围约束的全局向量检索和可选重排，并明确说明不递归遍历目录。因此方案不把“递归目录检索”写成已确认的当前机制。[检索机制](https://docs.openviking.ai/en/concepts/07-retrieval)

OpenViking 的记忆抽取允许编辑、合并或删除已有文件；若以后采用其后端，需要独立保留课程原始证据和历史 Memory，导出本组格式，并由 C 输出课程所需的关系判断。服务返回“找到相关内容”本身不能作为课程状态判断已完成的证据。[会话管理](https://docs.openviking.ai/en/concepts/08-session)

本阶段建议仅借鉴范围检索、分层读取和变更可追溯三个思路。直接引入服务是否有收益，需在相同开发集、模型、预算与指标下验证；不引用其公开分数替代本组实验，不把参考项目能力写成本组已实现能力。参考页面查阅于 2026-10-04，实现选型时应记录具体版本。
