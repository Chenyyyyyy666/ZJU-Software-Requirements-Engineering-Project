# 团队工作流 Team Workflow

> 版本：v0.1  
> 适用范围：本项目全体成员  
> 交付目标：保持 `main` 随时可交付，让每项工作都有负责人、证据和可追溯记录。

## 1. 协作总则

- 采用 **GitHub Flow**：`main` 是唯一交付主线，所有改动通过短生命周期分支和 Pull Request 合入。
- 仓库为私有仓库；`protect-main` Ruleset 保护默认分支 `main`。禁止直接推送、删除主干或强推覆盖历史。
- 一人一分支、一分支一件事；分支通常存活 1-3 天。优先为行动项建立 Issue，并在分支名和 PR 中关联编号。
- PR 至少由一位非作者成员 Approve 后才能合入；平台只允许 **Squash merge**，合并后删除分支。
- 项目不配置 CI，本地检查和 PR 中的验证证据是合并前的必要条件。

## 2. 一项工作的标准闭环

1. **计划**：在 Issue 或 `process/` 周计划中写明目标、负责人、备份、验收标准和截止时间。
2. **同步主干**：从最新 `main` 创建分支；开始提交前确认没有未处理的冲突。
3. **实现与小步提交**：一次提交只做一件事，保持改动可审查；涉及接口变化时先通知消费方。
4. **本地检查**：提交前由 `pre-commit` 自动运行 ruff 和大文件/私钥检查；PR 前至少执行：
   ```bash
   ruff check .
   ruff format --check .
   pytest -q
   ```
   涉及模型调用的测试默认使用 mock；真实调用需在 PR 中附命令输出或截图。
5. **提交 PR**：填写改动、原因、验证结果、影响范围和自检清单；超过 400 行应拆分，未完成但需要反馈时使用 Draft PR。
6. **审核与合入**：reviewer 检查代码、接口、测试证据和敏感信息；作者处理评论并 Resolve conversation。满足条件后使用 Squash merge。
7. **归档与复盘**：合并后删除分支；里程碑完成立即打 tag，过程材料当天存入 `process/`。

## 3. 分支、提交与 PR 规范

### 3.1 分支命名

格式为 `<type>/<issue-id>-<short-description>`，全小写、连字符分隔、不使用中文与空格、不超过 50 个字符。

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `feat/` | 新功能 | `feat/12-memory-extraction` |
| `fix/` | 缺陷修复 | `fix/34-json-encoding` |
| `docs/` | 文档或 slides | `docs/7-milestone1` |
| `refactor/` | 不改变行为的重构 | `refactor/20-retrieval-api` |
| `test/` | 测试补充 | `test/22-recall-eval` |
| `chore/` / `exp/` | 配置维护 / 探索实验 | `chore/5-ruff-setup` |

### 3.2 约定式提交

格式：`<type>(<scope>): <描述>`，描述用一句话说明做了什么，不加句号。常用类型为 `feat`、`fix`、`docs`、`test`、`refactor`、`chore`、`perf`、`style`。

```text
feat(memory): 抽取人物与时间字段
fix(eval): 修正无命中时的 Recall@K 计算
docs(milestone1): 补全团队分工与会议机制
```

破坏性变更在 type 或 scope 后加 `!`，并在正文或 footer 说明 `BREAKING CHANGE`。

### 3.3 PR 最低要求

PR 标题沿用约定式提交格式，因为 Squash merge 后标题会成为 `main` 上的提交信息。描述至少包含：

```markdown
改了什么
为什么改（Closes #编号）
怎么验证的（命令、结果、截图）
影响范围（是否影响他人模块的接口）
自检
- [ ] 本地跑过 lint 与测试
- [ ] 未提交密钥、数据或大文件
- [ ] 接口改动已通知消费方
```

## 5. 会议、记录与里程碑

- 每周召开一次项目周会，组织者固定为 `陈易`；会议聚焦进度、阻塞、接口变更和下一周行动项。
- 纪要由成员轮值，当天上传至 `process/`；每条行动项必须有负责人、截止时间和验收结果。
- 每个里程碑结束时复盘交付、延期、接手和流程问题，并同步 `README.md`、周计划和本表。

## 6. 冲突、质量与完成标准

1. 冲突只在个人分支解决：先同步最新 `main`，解决后重新运行本地检查，再推送。
2. 不合并未解决的冲突，不使用 `--no-verify`，不提交 API key、`.env`、数据集或模型输出大文件。
3. 两人同时需要修改同一文件时，以文件归属人为最终维护者；新增、移动或重命名顶层目录必须在周会上提出并由陈易执行。
4. 任务只有在代码或文档完成、验证证据已记录、PR 评论已处理、必要的交接和过程材料已归档后，才算完成。
5. 里程碑交付后立即打 tag，例如：
   ```bash
   git tag -a v0.1-milestone1 -m "Milestone 1 Team Workflow"
   git push origin v0.1-milestone1
   ```
